## Finding F8.2: JsonDataSource throws instead of converting when a node holds a CLR value (Guid, DateTimeOffset, char, NaN)

Location: `src/TruthWeaver.DataSources.Json/JsonDataSource.cs:153` (PLAUSIBLE, medium)

TryConvert calls value.GetValue<string>() whenever GetValueKind() is String. A JsonValue built from a CLR Guid or DateTimeOffset (JsonValue.Create or the JsonNode implicit conversions) reports kind String, but GetValue<string>() throws InvalidOperationException for it. A CLR double NaN makes ToJsonString() at line 185 throw. The number branch is written to avoid this problem (comment at lines 177-178), but the string branch is not. ADR-0006 decision 9 says the source reports such failures as data, not as exceptions. (PLAUSIBLE: depends on the System.Text.Json JsonValuePrimitive<T>.TryGetValue behavior.)

### Failure scenario

JsonDataSource.Create(new JsonObject { ["id"] = Guid.NewGuid() }) and a rule isOwner(id: from("doc", "$.id")) with a Guid argument. QueryAsync throws InvalidOperationException, and the evaluator backstop records a SourceError fault (term is Unknown). The docs say a matched string converts to a Guid. YamlDataSource never hits this because it builds string-backed values.

### Expected behavior

Read a String-kind value through TryGetValue<string> and fall back to the node's JSON text (ToJsonString, unquoted), or return an UnsupportedType or SourceFailure result. Do not throw.

Decision: report as a typed failure (data), not a silent fallback to raw JSON text. Consistent with this effort's established preference (ultra-review ticket 15) for surfacing a diagnostic over guessing at a conversion — a `Guid`/`DateTimeOffset`/`char` silently rendered as its JSON text could itself be a surprising, differently-shaped string than a caller expects from `ToString()`.

## Agent Brief

**Category:** bug
**Summary:** `JsonDataSource` throws `InvalidOperationException` instead of returning a typed query failure when a queried node holds a CLR value (`Guid`, `DateTimeOffset`, `char`) that reports a `String` JSON kind but can't actually be read as a string, or a CLR `double.NaN`.

**Current behavior:** Converting a matched node to a requested type calls the JSON value's string getter whenever the node's reported kind is `String`. A `JsonValue` built from a CLR `Guid`, `DateTimeOffset`, or `char` reports kind `String` but throws when read as a string, because the underlying value isn't textual. A CLR `NaN` throws when the number branch tries to render it as JSON text. Both cases propagate as an uncaught exception instead of the documented "report failures as data" contract (ADR-0006 decision 9).

**Desired behavior:** Querying a node that holds one of these CLR values never throws. It returns the same kind of typed query failure (e.g. `UnsupportedType`) the data source already uses for other unsupported conversions, so the evaluator's existing fault-handling takes over exactly as it does for other source failures.

**Key interfaces:**
- `JsonDataSource`'s value-conversion path (`TryConvert` and its number branch) needs to catch or detect these cases and return a failure `DataQueryResult`, not let the underlying exception escape.

**Acceptance criteria:**
- [ ] Querying a node built from a CLR `Guid` returns a failure result, not a thrown exception.
- [ ] The same holds for `DateTimeOffset`, `char`, and CLR `NaN`.
- [ ] A rule term reading such a value gets a fault and an `Unknown` result through the normal fault-handling path, not a crash.
- [ ] A normal string-kind JSON value (not CLR-backed) is unaffected.
- [ ] The validation list in `CLAUDE.md` passes.

**Out of scope:**
- `YamlDataSource`, which already builds string-backed values and doesn't hit this.
