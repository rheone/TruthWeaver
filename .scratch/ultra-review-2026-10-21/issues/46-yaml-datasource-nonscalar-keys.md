## Finding F8.10: YAML mapping keys that are not scalars all collapse to an empty-string key, and the data is silently overwritten

Location: `src/TruthWeaver.Yaml/YamlDataSource.cs:140` (PLAUSIBLE, low)

The comment says a non-scalar key 'is read as its text', but the code maps every sequence or mapping key to string.Empty. YamlDotNet compares keys structurally, so it does not report [a] and [b] as duplicates. Both become "" and the later value replaces the earlier one with no error. The same data as JSON cannot be expressed this way, and Parse and TryParse report duplicate keys as errors only for scalar keys.

### Failure scenario

YAML '? [a]\n: 1\n? [b]\n: 2\n' parses without error. $[''] matches 2, and the first entry is lost. TryParse returns true.

### Expected behavior

Reject a non-scalar mapping key with a YamlException (positioned, no content), consistent with the duplicate-key rule.

## Agent Brief

**Category:** bug
**Summary:** A YAML mapping key that isn't a scalar (a sequence or nested mapping used as a key) collapses to an empty-string key for every such key in the document, so a second non-scalar key silently overwrites the first entry's value with no error.

**Current behavior:** `YamlDataSource`'s key-reading maps every non-scalar key to `string.Empty`, despite a comment claiming it's "read as its text." Because YamlDotNet compares keys structurally (not by this collapsed text), two different non-scalar keys aren't flagged as duplicates by the parser — they just both end up stored under `""`, and the later one silently wins. The data source's existing duplicate-key detection only catches scalar-key duplicates.

**Desired behavior:** A non-scalar mapping key is rejected with a positioned `YamlException` (no document content in the message, consistent with the existing duplicate-key rejection's style), instead of silently collapsing and overwriting.
