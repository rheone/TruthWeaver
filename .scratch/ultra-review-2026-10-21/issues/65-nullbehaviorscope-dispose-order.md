## Finding F7.7: Disposing scopes out of order can bring back a disposed NullBehaviorScope

Location: `src/TruthWeaver.Predicates/NullBehaviorScope.cs:81` (PLAUSIBLE, low)

Dispose sets Current.Value to this.parent without checking that this scope is the current one. If an outer scope is disposed before an inner one, disposing the inner scope later restores the outer scope, which is already disposed, as the ambient default.

### Failure scenario

`var a = NullBehaviorScope.Begin(NullBehavior.False); var b = NullBehaviorScope.Begin(PredicateFamily.Type, NullBehavior.Unknown); a.Dispose(); b.Dispose();` Both scopes are now disposed, but Current is `a`. Every later factory call on that flow resolves Default to False, not to the documented no-scope default, Unknown.

### Expected behavior

Dispose only restores the parent when this scope is Current.Value, or unwinds past disposed ancestors. An out-of-order dispose should not leave a disposed scope in effect.

## Agent Brief

**Category:** bug
**Summary:** Disposing `NullBehaviorScope` instances out of order (an outer scope disposed before an inner one) can restore an already-disposed outer scope as the ambient current scope once the inner one is disposed later, instead of the documented no-scope default.

**Current behavior:** `Dispose` unconditionally sets the ambient current scope back to its own recorded parent, without checking whether this scope is still the current one. If an outer scope is disposed first, then an inner scope disposed afterward restores the (already-disposed) outer scope as current — leaving a disposed scope in effect instead of falling back to the documented no-scope default.

**Desired behavior:** Disposing a scope only restores its parent when it's actually the current scope (or disposal correctly unwinds past any already-disposed ancestors). An out-of-order dispose never leaves a disposed scope active as the ambient current one.

## Resolution (2026-11-01)

Reproduced as written (after `a.Dispose(); b.Dispose();` the ambient scope was `a` and a string factory answered False). A second effect of the same line came up while writing the test: disposing `a` while `b` was open set the ambient scope to `a`'s parent, so the still-open `b` stopped applying too.

`NullBehaviorScope.Dispose` now marks the scope disposed and moves the ambient pointer only when the scope is the current one, unwinding past every disposed ancestor to the nearest open scope (or none). `Resolve` skips a disposed scope that is still in the chain. So an outer scope disposed first stops applying at once, an inner scope stays in effect until it ends, and a disposed scope is never current again. The properly nested case is unchanged.

Tests (`NullBehaviorScopeTests`): `Dispose_OuterBeforeInner_LeavesNoScopeInEffect_Test` (the ticket's scenario) and `Dispose_OuterWhileInnerIsOpen_StopsOnlyTheOuterScope_Test`, both red before and green after; the existing nesting tests still pass.

Docs: `docs/predicates.md` (null selected values: what disposing a scope does, in and out of order).
