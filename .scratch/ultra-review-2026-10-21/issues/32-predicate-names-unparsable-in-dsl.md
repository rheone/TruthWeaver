## Finding F8.3: Registry and generator accept predicate and collection names that rule text cannot express, so a JSON-compiled rule prints unparsable DSL

Location: `src/TruthWeaver/Registry/PredicateRegistryBuilder.cs:124` (PLAUSIBLE, medium)

AddDescriptor rejects only reserved words and case duplicates. It does not check that the name is a DSL identifier (Lexer.cs:33-40: a letter or '_' first, then letters, digits and '_'). Empty names and names with '-', '.' or spaces register. TreeFormatReader.ReadTerm accepts any string, and CanonicalPrinter writes the name verbatim. AddCollection (line 89) has no reserved-word or identifier check at all. The generator (PredicateRegistrationGenerator.Distinct) checks only reserved words.

### Failure scenario

Register a predicate named "has-role". CompileJson({"predicate":"has-role"}) succeeds. CompiledRule.PrintRuleText() emits has-role, which re-parses as has - role and fails. RuleFormat promises that all three formats round-trip without loss. AddCollection("and", ...) registers a binding that no FORALL(x IN and, ...) can name, with no error.

### Expected behavior

Reject a predicate or collection name that is not a DSL identifier, or is reserved, at registration (ArgumentException), and add a matching generator diagnostic.

## Agent Brief

**Category:** bug
**Summary:** Registering a predicate or collection with a name that isn't a valid DSL identifier (contains `-`, `.`, a space, or is empty) succeeds, compiles from JSON/YAML, and then prints DSL text that fails to re-parse as the same predicate — breaking the documented round-trip guarantee.

**Current behavior:** Predicate registration rejects only reserved words and case-duplicate names; it doesn't check that the name is a valid DSL identifier (letter or `_` first, then letters/digits/`_`). Collection registration has no name check at all. A predicate or collection registered with a name like `"has-role"` compiles successfully from JSON/YAML, but `PrintRuleText()` emits it verbatim, and re-parsing that DSL text splits it into unrelated tokens (e.g. `has - role`), failing to recompile as the same predicate.

**Desired behavior:** Registering a predicate or collection name that isn't a valid DSL identifier, or is a reserved word, fails at registration with a clear exception — the same place the existing reserved-word check already fails fast — rather than succeeding and breaking later at print/re-parse time. The predicate-registration source generator reports the equivalent diagnostic for a name it can't express.

**Key interfaces:**
- Predicate registration's name validation (currently reserved-word and case-duplicate only) needs a DSL-identifier check added.
- Collection registration needs the same identifier/reserved-word check it currently lacks entirely.
- The predicate-registration source generator needs a matching diagnostic.

**Acceptance criteria:**
- [ ] Registering a predicate named `"has-role"` (or any other non-identifier name) throws at registration with a clear message, instead of succeeding and breaking at round-trip.
- [ ] The same holds for collection registration.
- [ ] A reserved word is still rejected (no regression).
- [ ] A valid identifier name is unaffected.
- [ ] The source generator reports an equivalent diagnostic for a name it can't express.
- [ ] The validation list in `CLAUDE.md` passes.

**Out of scope:**
- Making the DSL able to express a wider range of names instead — considered and explicitly not chosen; the DSL's identifier grammar is not changing.
