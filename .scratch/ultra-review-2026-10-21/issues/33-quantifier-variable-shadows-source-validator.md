## Finding F8.4: A quantifier variable that shadows a declared source keeps the hidden source's validator for element queries

Location: `src/TruthWeaver/Registry/CollectionBinding.cs:251` (PLAUSIBLE, medium)

DeclareElementSource copies the outer declarations and then calls declared.Add(variable), which keeps an existing validator. At evaluation, WithElementSource (line 268-276) makes the element source win over the outer source of the same name. So compile-time syntax checks for from(variable, ...) run in the dialect of a source the body can never reach. The ADR-0010 amendment states both rules (keep the validator, the element wins), and together they contradict ADR-0006 decision 4: a validator checks a query in that source's dialect.

### Failure scenario

The outer "user" is declared with JsonQueryValidator.Instance. A collection "orders" has an elementSource that projects to a custom key-value source whose dialect is "total". The rule FORALL(user IN orders, over(limit: from("user", "total"))) fails to compile with TRE0025 (not valid JSONPath), although the query is valid for the source it reaches at evaluation. The reverse case also happens: a query that is malformed for the element source is not flagged because JSONPath accepts it.

### Expected behavior

Inside the body, declare the variable without a validator (replace the outer entry), or report a shadowing diagnostic when the variable name equals a declared source.

## Comments

> *This was generated by AI during triage.*

Decision: drop the validator for the shadowed name inside the quantifier body, rather than rejecting the shadowing itself as a compile error. Never rejecting a query that would work, and never accepting one that won't, is the correct trade against ADR-0006 decision 4 ("a validator checks a query in that source's dialect") — no validator at all is honest about there being none, where the outer validator is actively wrong.

## Agent Brief

**Category:** bug
**Summary:** When a quantifier's element variable shares a name with a declared outer data source, the quantifier body keeps the outer source's compile-time query-syntax validator for `from(variable, ...)` references, even though the element source wins at evaluation — so compile-time syntax checks run in the wrong source's dialect, both false-rejecting valid element-source queries and false-accepting queries that are malformed for the element source.

**Current behavior:** Declaring a quantifier's element source copies the outer source declarations and adds the element binding under the variable name, but if that name already exists (shadowing an outer source), the existing (outer) validator is kept rather than replaced. At evaluation, the element source correctly wins for that name. The mismatch means a query valid in the element source's dialect can fail to compile (checked against the outer source's dialect instead), and a query malformed for the element source can pass compile-time validation (because it happens to be valid outer-source syntax).

**Desired behavior:** Inside a quantifier body, a variable name that shadows a declared outer source gets no compile-time query-syntax validator for that name — consistent with there being no single dialect to check against at compile time when the variable's own element source isn't yet known to carry one, and matching that the element source (not the outer source) is what resolves at evaluation.

**Key interfaces:**
- Quantifier element-source declaration (`DeclareElementSource` or equivalent) needs to replace, not keep, any existing validator entry for the shadowing variable name.

**Acceptance criteria:**
- [ ] A quantifier variable that shadows an outer source name, with an element source whose query dialect differs from the outer source's, compiles a query valid in the element source's dialect without a false compile-time rejection.
- [ ] A query malformed for the element source but valid in the outer source's dialect is no longer falsely accepted at compile time (no validator falsely approves it either; at minimum, the previous false-accept behavior is not preserved).
- [ ] A quantifier variable that does *not* shadow any outer source is unaffected.
- [ ] The validation list in `CLAUDE.md` passes.

**Out of scope:**
- Rejecting the shadowing itself as a compile error — considered and explicitly not chosen.
- Adding a validator for the element source's own dialect (a larger feature; this ticket only removes the wrong one).
