## Finding F7.4: Calendar predicates fault on a valid instant near DateTimeOffset.MinValue/MaxValue, including default(DateTimeOffset)

Location: `src/TruthWeaver.Predicates/DateTimePredicates.FixedOffset.cs:344` (PLAUSIBLE, medium)

BindTimeWindow (line 344), BindMonths (line 510) and BindDays (line 571) call instant.ToOffset(offset). ToOffset throws ArgumentOutOfRangeException when the local clock time would fall outside the DateTime range. A selected instant that is valid but near either end of the range therefore gives Unknown plus a Fault, not a definite answer. It also counts toward FaultBudget. No doc mentions this edge.

### Failure scenario

The selector returns a non-nullable DateTimeOffset field that was never set, so the value is default(DateTimeOffset), 0001-01-01T00:00:00Z. The rule is `isWeekday(days: ["Monday"], offset: "-05:00")`. ToOffset(-5h) throws, so the answer is Unknown with one fault. With offset "Z" the same value answers definitely, and DateTimeOffset.MaxValue with a positive offset fails the same way.

### Expected behavior

Compute the local calendar fields from UtcDateTime.Ticks + offset.Ticks without building a DateTimeOffset. Or clamp the value and document the behavior, so that every representable instant gets a definite True or False.

## Agent Brief

**Category:** bug
**Summary:** Calendar predicates (time-window, month, and day-of-week checks) fault instead of answering definitely for a valid instant near `DateTimeOffset.MinValue`/`MaxValue` — including `default(DateTimeOffset)` — because converting to the target offset via `DateTimeOffset.ToOffset` throws when the resulting local clock time would fall outside the representable range.

**Current behavior:** Each calendar predicate converts the selected instant to the configured UTC offset by constructing a new `DateTimeOffset` at that offset. Near either end of the representable range, that conversion throws `ArgumentOutOfRangeException`, which the evaluator turns into a fault and an `Unknown` result — even though the instant and the requested offset are both individually valid, and the local calendar day/weekday/time is well-defined.

**Desired behavior:** Every representable `DateTimeOffset` instant, combined with any valid offset, produces a definite `True` or `False` from these predicates — never a fault from this cause. Compute the local calendar fields (date, day of week, time of day) directly from the instant's UTC ticks plus the offset's ticks, without constructing an intermediate `DateTimeOffset` that could fall outside the representable range.

**Key interfaces:**
- The shared local-time computation used by the time-window, month, and day-of-week predicate families (wherever `ToOffset` is currently called) needs to produce calendar fields without that intermediate conversion.

**Acceptance criteria:**
- [ ] `default(DateTimeOffset)` with an offset like `-05:00` gives a definite, correct answer instead of a fault.
- [ ] `DateTimeOffset.MaxValue` with a positive offset gives a definite, correct answer instead of a fault.
- [ ] The computed calendar day/weekday/time matches what the equivalent in-range conversion would give, for instants where both are computable.
- [ ] The validation list in `CLAUDE.md` passes.

**Out of scope:**
- Any predicate outside the time-window/month/day-of-week families.
