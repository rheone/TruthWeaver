## Finding F9.4: Term memo is shared across rules compiled with different registries

Location: `src/TruthWeaver.Policies/PolicySet{TContext}.cs:101` (PLAUSIBLE, medium)

The shared EvaluationState keys Memo by (scope, TermIdentity) and CollectionMaterializations by (scope, collection name). Neither key includes the registry. PolicySet accepts rules from any compiler and does not check that they share one PredicateRegistry. docs/policies.md states this ('whichever rule compiled them'). The result is that one rule's answer can stand in for a different predicate or a different compile mode.

### Failure scenario

The set target is compiled in Lenient mode against a registry where `isAdmin` is missing. It memoizes Unknown for isAdmin and records a fault. A permit policy compiled in Strict mode with a registered `isAdmin` then hits the memo: the real predicate never runs, the policy is Unknown, and the set is Indeterminate. In the same way, two registries that bind the name `isAdmin` to different implementations reuse whichever ran first.

### Expected behavior

Either the set rejects rules whose registries differ (or are incompatible), or the memo key includes the registry identity, so each rule evaluates its own predicates.

## Comments

> *This was generated by AI during triage.*

Decision: widen the memo key to include registry identity, rather than rejecting rules whose registries differ. This is strictly safer and non-breaking — no `PolicySet` that currently constructs successfully would newly fail; it just stops incorrectly sharing one rule's answer with a different rule's predicate.

## Agent Brief

**Category:** bug
**Summary:** A `PolicySet`'s shared evaluation state memoizes a term's answer by `(scope, TermIdentity)` only, with no registry component, so two rules in the same set compiled against different registries (different compile mode, or different predicate implementations bound to the same name) can have one rule's memoized answer silently stand in for the other's.

**Current behavior:** The shared `EvaluationState`'s term memo and collection-materialization cache key only on scope and term/collection identity. `PolicySet` accepts rules from any compiler and doesn't require them to share one registry. When two rules happen to produce the same `TermIdentity` for what are actually different predicates (different registry, different compile mode, or a different implementation bound to the same name), the memo returns whichever rule evaluated that identity first — silently substituting a different predicate's answer, or a different compile mode's leniency, into a rule that never actually ran its own predicate.

**Desired behavior:** Each rule's predicate evaluates independently, scoped to its own registry — a different rule using a different registry (or a different implementation of the same-named predicate) never reuses another rule's memoized answer for what is, to the engine, the "same" term identity but a different underlying predicate.

**Key interfaces:**
- The shared `EvaluationState`'s memo and collection-materialization cache keys need a registry-identity component alongside scope and term/collection identity.

**Acceptance criteria:**
- [ ] Two rules in one `PolicySet`, compiled against different registries that bind the same predicate name to different behavior (or compiled in different modes against a registry missing a predicate in one case), each evaluate their own predicate independently — neither's answer leaks into the other.
- [ ] A `PolicySet` whose rules share one registry (the common case) is unaffected in behavior or performance beyond the memo key's extra component.
- [ ] The validation list in `CLAUDE.md` passes.

**Out of scope:**
- Rejecting or validating registry compatibility at `PolicySet` construction time — considered and explicitly not chosen in favor of the always-correct memo-key fix.
