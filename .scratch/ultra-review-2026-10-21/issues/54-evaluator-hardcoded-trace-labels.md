## Finding F4.7: Evaluator hard-codes operator trace labels instead of reading OperatorDefinitions

Location: `src/TruthWeaver/Evaluation/Evaluator.cs:178` (PLAUSIBLE, low)

Evaluated nodes get literal labels ("AND", "OR", "COALESCE", "XOR", "PARITY", "ExactlyOne", and $"{OpName}({K})" for thresholds). Skipped nodes go through TraceText.Of, which reads OperatorDefinitions.Label. CLAUDE.md says the Evaluator trace labels come from that table, and RuleCoverageAccumulator compares trace text against TraceText output.

### Failure scenario

A change to the PARITY label in OperatorDefinitions (for example "Parity") changes skipped nodes and coverage text, but evaluated nodes still say "PARITY". Trace tree labels then disagree, and coverage matching against the trace breaks.

## Agent Brief

**Category:** bug
**Summary:** Evaluated trace nodes use literal, hard-coded operator labels ("AND", "OR", "PARITY", etc.), while skipped nodes read the same label from `OperatorDefinitions` — so a label change there updates skipped-node trace text but not evaluated-node trace text, producing a trace tree with inconsistent labels for the same operator.

**Current behavior:** The evaluator builds evaluated-node trace labels from literal strings in its own code. Skipped nodes go through a shared helper that reads the label from `OperatorDefinitions`. `CLAUDE.md` documents that evaluator trace labels come from that table — only the skipped-node path actually does.

**Desired behavior:** Evaluated-node trace labels are read from `OperatorDefinitions`, the same source skipped-node labels already use, so a label change in one place updates both consistently and `RuleCoverageAccumulator`'s trace-text comparison stays correct regardless of which path produced a given node.

**Key interfaces:**
- The evaluator's trace-label construction for evaluated AND/OR/COALESCE/XOR/PARITY/ExactlyOne/threshold nodes.
