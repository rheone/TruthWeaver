## Finding F7.3: Literal regex pattern is checked with no options when the flags come from a data source, so a valid rule fails to compile

Location: `src/TruthWeaver.Predicates/RegexPredicates.cs:233` (PLAUSIBLE, medium)

ValidateArguments reads the flags with TryGetString. An omitted flags argument is filled with its default "", so a missing flags value at compile time means it is deferred to a data source. In that case `options` stays RegexOptions.None and the literal pattern is still validated with Cache.Validate. regex-ismatch.md says a data-source flags value is checked at evaluation and that a pattern valid only with 'x' compiles. The validator should skip the pattern check when args.IsDeferred("flags").

### Failure scenario

Rule: `codeIsMatch(pattern: "^a+ # one or more (a's", flags: from("request", "$.flags"))`, where the data source supplies "x". Under 'x' the '(' is inside a comment and the pattern is valid. Under None the paren is unbalanced, so the compiler reports TRE0026 and rejects a rule that would evaluate correctly.

### Expected behavior

When flags is deferred, do not validate the literal pattern at compile time. Leave the check to evaluation, where the real options are known.

## Agent Brief

**Category:** bug
**Summary:** A regex predicate whose `flags` argument is deferred to a data source still has its literal `pattern` validated at compile time under no flags, so a pattern that's only valid under a flag the data source will supply (e.g. `x` for free-spacing) wrongly fails to compile.

**Current behavior:** When `flags` is omitted (deferred to a data source), compile-time validation checks the literal pattern under `RegexOptions.None` regardless. A pattern written assuming the free-spacing (`x`) flag — valid once that flag is applied — is rejected at compile time even though it would evaluate correctly once the real flags are known.

**Desired behavior:** When the flags argument is deferred, compile-time validation of the literal pattern is skipped; the pattern is checked at evaluation time instead, once the real flags are known. A rule whose flags are a literal (not deferred) is validated at compile time exactly as before.

**Key interfaces:**
- The regex predicate's compile-time argument validation needs to check whether the flags argument is deferred before validating the pattern against a fixed option set.

**Acceptance criteria:**
- [ ] A pattern valid only under a flag supplied by a deferred `flags` argument compiles successfully.
- [ ] A pattern with a literal (non-deferred) `flags` argument is still validated at compile time as before.
- [ ] A genuinely malformed pattern (invalid under any flag combination) still fails at evaluation time with a clear fault.
- [ ] The validation list in `CLAUDE.md` passes.

**Out of scope:**
- Changing how flags are validated once known at evaluation time (already correct).

### Resolution

`RegexPredicates.ValidateArguments` skips the literal-pattern check when `args.IsDeferred("flags")`. A literal or omitted `flags` is validated as before. Tests: `RegexPredicatesTests`. Docs: `docs/strong-k3/predicates/regex-ismatch.md`.
