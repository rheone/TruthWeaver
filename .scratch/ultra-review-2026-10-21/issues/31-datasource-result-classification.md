## Finding F8.1: TryGetAsync/GetAsync classify an object, array or null match as SourceError; a variable classifies the same match as TypeMismatch

Location: `src/TruthWeaver/Building/DataSourceExtensions.cs:56` (PLAUSIBLE, medium)

TryGetAsync maps every DataQueryResult error kind, UnsupportedType included, to VariableFailureKind.SourceError. The evaluator maps UnsupportedType to TypeMismatch (Evaluator.cs:801-804). docs/data-sources.md:246-252 says GetAsync 'converts like a variable would' and lists TypeMismatch as a failure kind. So the eager read and the deferred read disagree on the same data.

### Failure scenario

JsonDataSource.Parse("{\"limits\":{\"age\":null}}").TryGetAsync<long>("$.limits.age") returns FailureKind = SourceError. A rule term ageAtLeast(min: from("cfg", "$.limits.age")) against the same document records a TypeMismatch fault. Host code that branches on FailureKind (for example, retry on SourceError) retries a data problem that can never succeed.

### Expected behavior

Map UnsupportedType to TypeMismatch in TryGetAsync, as Evaluator.QuerySourceUncachedAsync does, so both paths report one kind.

## Finding L5.6: A data source that answers QueryAsync with NoMatch or AmbiguousMatch is reported as a source error, not missing/ambiguous

Location: `src/TruthWeaver/Evaluation/Evaluator.cs:801` (PLAUSIBLE, low)

`QuerySourceUncachedAsync` maps every `DataQueryErrorKind` other than `UnsupportedType` to `VariableFailureKind.SourceError` (Evaluator.cs:801-807), so a custom `IDataSource` that returns `DataQueryResult.Failure(DataQueryErrorKind.NoMatch, ...)` or `AmbiguousMatch` from `QueryAsync` (the API accepts any kind) gets the trace word "source error" and a `SourceError` fault instead of "missing"/"ambiguous". The enum doc (DataQueryErrorKind.cs:15-19) says those two kinds are for `ScopeAsync`, but nothing in `DataQueryResult.Failure` enforces it and docs/data-sources.md "Writing your own data source" does not say to return `Empty()` for no match.

### Failure scenario

A host writes a database-backed source that returns `Failure(NoMatch, "no row")` when a scalar query finds nothing. The trace reads `[from("db", "$.x"): source error]` and `Fault.Exception.Kind` is `SourceError`; an operator triages it as an outage rather than missing data, which is the documented `Missing` outcome for the same situation in the JSON source.

### Expected behavior

Either map `NoMatch` to `Missing` and `AmbiguousMatch` to `Ambiguous`, or document in `DataQueryResult.Failure` and the data-sources guide that a query source must answer no match with `Empty()` and that those two kinds are scope-only.

Decision for L5.6: map `NoMatch`→`Missing` and `AmbiguousMatch`→`Ambiguous` in the evaluator's classification, rather than only documenting that custom sources must avoid returning these kinds from `QueryAsync`. This is the more robust choice — it classifies a custom data source's query failure correctly without requiring every implementer to already know an undocumented restriction, and it's consistent with the primary fix (mapping `UnsupportedType`→`TypeMismatch`) in the same ticket.

## Agent Brief

**Category:** bug
**Summary:** Three related classification mismatches between the eager (`TryGetAsync`/`GetAsync`) and deferred (variable/evaluator) read paths for the same underlying data-source failure, all against the documented contract that both paths classify failures the same way.

**Current behavior:**
- `TryGetAsync`/`GetAsync` map every `DataQueryResult` error kind, including `UnsupportedType`, to `SourceError`. The evaluator's deferred-variable path maps `UnsupportedType` specifically to `TypeMismatch`. The same underlying data disagrees on its failure kind depending on which path reads it.
- The evaluator maps every `DataQueryErrorKind` other than `UnsupportedType` to `SourceError`, including `NoMatch` and `AmbiguousMatch` — kinds the enum's own documentation says are meant for `ScopeAsync`, not `QueryAsync` — so a custom data source that answers a scalar query with `NoMatch`/`AmbiguousMatch` gets a misleading "source error" fault instead of "missing"/"ambiguous".

**Desired behavior:**
- `TryGetAsync`/`GetAsync` map `UnsupportedType` to `TypeMismatch`, matching the evaluator's deferred-read path, so both paths agree on the same data.
- The evaluator maps `NoMatch` to `Missing` and `AmbiguousMatch` to `Ambiguous`, matching the outcome a well-behaved `ScopeAsync`-style source already gets for the equivalent situation, instead of folding both into `SourceError`.

**Key interfaces:**
- `DataSourceExtensions.TryGetAsync`'s error-kind mapping.
- The evaluator's `QuerySourceUncachedAsync` error-kind mapping.

**Acceptance criteria:**
- [ ] `TryGetAsync<T>` on an `UnsupportedType` result returns `TypeMismatch`, not `SourceError`.
- [ ] A custom data source answering `QueryAsync` with `NoMatch` produces a `Missing` fault/outcome, not `SourceError`.
- [ ] The same holds for `AmbiguousMatch` → `Ambiguous`.
- [ ] Host code branching on failure kind (e.g. retrying only on `SourceError`) now sees the correct, retry-appropriate classification for each case.
- [ ] The validation list in `CLAUDE.md` passes.

**Out of scope:**
- Any other `DataQueryErrorKind` value not named above.
