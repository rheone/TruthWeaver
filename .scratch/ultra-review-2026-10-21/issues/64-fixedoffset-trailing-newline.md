## Finding F7.5: FixedOffsetText regexes use '$', so a trailing newline is accepted

Location: `src/TruthWeaver.Predicates/FixedOffsetText.cs:142` (PLAUSIBLE, low)

OffsetPattern, TimeOfDayPattern and DurationPattern anchor with '$'. Without Multiline, '$' also matches before a final '\n'. The class remarks say only one spelling per value is accepted, and the docs list exact forms.

### Failure scenario

A YAML or JSON rule gives `offset: "+05:30\n"` or `start: "09:00\n"`. The compile-time validator accepts it with no TRE0026, and evaluation uses +05:30 or 09:00. A data-source value with a stray newline is accepted the same way. The documented grammar should reject both.

### Expected behavior

Anchor with \z, or use RegexOptions.NonBacktracking with \z, so only the exact documented form matches.

## Agent Brief

**Category:** bug
**Summary:** `FixedOffsetText`'s offset, time-of-day, and duration regexes anchor with `$`, which (without `Multiline`) also matches immediately before a final newline — so a value with a stray trailing newline parses successfully, contrary to the documented "one spelling only" contract.

**Current behavior:** `OffsetPattern`, `TimeOfDayPattern`, and `DurationPattern` all end with `$`. A string like `"+05:30\n"` or `"09:00\n"` parses as if the newline weren't there, because `$` matches before a trailing `\n` by default.

**Desired behavior:** Only the exact documented form matches — a trailing newline (or any other trailing character) makes the parse fail, the same as any other malformed input.

**Key interfaces:**
- `FixedOffsetText`'s `OffsetPattern`, `TimeOfDayPattern`, `DurationPattern`.

**Acceptance criteria:**
- [x] A value with a trailing newline (e.g. `"+05:30\n"`, `"09:00\n"`) fails to parse for all three patterns.
- [x] The exact documented forms (no trailing content) still parse correctly.
- [x] The validation list in `CLAUDE.md` passes.

## Resolution (2026-11-01)

Per the Decision, `OffsetPattern`, `TimeOfDayPattern` and `DurationPattern` in `src/TruthWeaver.Predicates/FixedOffsetText.cs` now end in `\z` in place of `$`, so a trailing line break no longer matches. Reproduced first: the validator accepted `"+05:30\n"`, `"09:00\n"`, `"17:00\n"` and `"PT8H\n"`. A data-source value goes through the same parse, so it is rejected the same way at evaluation. `TimeZoneNamePattern` is unchanged: it only picks the wording of the error message for a value that is already rejected.

Tests (`FixedOffsetPredicatesTests`): `ArgumentValidator_ValueWithTrailingLineBreak_ReportsAProblem_Test` (red before for all four arguments, green after) and `ArgumentValidator_ExactValues_ReportsNoProblem_Test`.

Docs: `docs/strong-k3/predicates/README.md` (Fixed offsets) now states that a value must be exactly one documented form, with nothing after it.
