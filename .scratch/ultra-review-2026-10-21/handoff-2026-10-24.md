### Non-obvious things the ticket-03 fix surfaced (relevant to later tickets in this branch)

- `CompilerOptions` is now exposed as `internal CompilerOptions Options` on `RuleCompiler` so
  `TruthWeaver.Yaml` (via `InternalsVisibleTo`) can read `MaxDepth`. Reuse this rather than re-threading
  options a different way for tickets 04/05/23 if they also need `CompilerOptions` values inside the YAML
  or definition-expansion path.
- **YamlDotNet gotcha**: `YamlNode.GetHashCode()`/`Equals` are *structural* (recurse into every
  descendant). Any ancestor/visited set keyed on `YamlNode` **must** use
  `ReferenceEqualityComparer.Instance`, or it re-triggers the exact stack-overflow/exponential-cost
  problem these tickets are about. `YamlDataSource.ToJson` already does this correctly - copy that
  pattern for tickets 04/05.
- YamlDotNet's own `YamlStream.Load` has its own undocumented recursion ceiling (~1900-2000 levels on
  this stack size) that is outside this repo's control. Don't write a test that relies on exceeding it.
- `RuleNodeCompiler.Build`'s existing `MaxDepth` check is still load-bearing for one case ticket 03's
  parse-time guard does not reach: a `let` chain that is shallow as written but deep after
  `DefinitionExpander` inlines uses. That's exactly what **ticket 04** is about - don't treat it as
  already fixed.
- When a depth/size guard trips mid-parse, the recursive-descent parser is left with unconsumed tokens;
  unwinding naively adds spurious extra diagnostics. Ticket 03's fix truncates diagnostics back to the
  one limit-exceeded entry once the guard trips - watch for the same artifact in ticket 04's `let`-expansion
  guard and ticket 10/24's node-budget guards.
