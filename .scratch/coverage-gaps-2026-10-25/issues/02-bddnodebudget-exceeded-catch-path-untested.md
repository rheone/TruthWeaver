## Gap

`Analyzer.Profile` (`src/TruthWeaver/Analysis/Analyzer.cs:205-219`) and `Analyzer.BddNodeCount`
(`:231-248`) each wrap their BDD build in a `try`/`catch (BddNodeBudgetExceededException) { return null; }`.
`BddNodeCount`'s own doc comment calls this "ticket 24" - the node-budget guard this very branch
(`ultra-review/crash-and-blowup-fixes`) just added to stop the analysis BDD readers from running unbounded
(ticket 24: "Give the analysis BDD readers a node budget"). Both catch blocks (lines 215-217 and 244-246)
are uncovered: nothing in the solution's test suite drives a tree through either method large/shaped enough
to actually exceed `BddManager.DefaultMaxBddNodes` and hit the catch, rather than the term-count short-circuit
a few lines above it (`DistinctTerms(root).Count > maxTerms`, which is covered).

A guard added specifically to prevent unbounded blowup, with no regression test proving it actually catches
the exception and returns `null` instead of letting the exception (or an unbounded build) propagate, is a
critical gap for this exact branch's own purpose.

## Missing scenario

A rule shaped to build a dual-rail BDD that exceeds `BddManager.DefaultMaxBddNodes` while staying under
`maxTerms` (so it reaches the BDD build, not the earlier `DistinctTerms` short-circuit) for both
`Analyzer.Profile` and `Analyzer.BddNodeCount`, asserting each returns `null` rather than throwing.

## Agent Brief

**Category:** enhancement
**Summary:** Add regression tests proving `Analyzer.Profile` and `Analyzer.BddNodeCount` return `null` when building the shared BDD would exceed the internal node budget, instead of letting the exception escape untested.

**Current behavior:**
When a rule's distinct-term count is within the configured cap but building its shared dual-rail BDD for that term ordering and rule shape would still exceed the analyzer's internal node budget, `Analyzer.Profile` and `Analyzer.BddNodeCount` each catch the node-budget exception and return `null`. No test currently drives either method into that branch: existing coverage only exercises the term-count short-circuit that runs before the BDD build, and the sibling node-budget tests exercise other analysis entry points (rule equivalence, implication, overlap, set analysis, diff), not these two.

**Desired behavior:**
A rule shaped so its distinct-term count is at or below the cap passed to `Profile`/`BddNodeCount`, but whose shared BDD construction for that term ordering and rule shape exceeds the node budget, causes each method to return `null` rather than throwing or hanging.

**Key interfaces:**
- `Analyzer.Profile(Expression root, int maxTerms)` returning `ValueProfile?` — returns `null` on node-budget exceeded, same as it already does on term-count exceeded.
- `Analyzer.BddNodeCount(Expression root, int maxTerms)` returning `int?` — returns `null` on node-budget exceeded, same as it already does on term-count exceeded.

**Acceptance criteria:**
- [ ] A test builds a rule tree whose distinct-term count is within `maxTerms` but whose shared BDD construction exceeds the node budget, and asserts `Analyzer.Profile` returns `null`.
- [ ] An equivalent test (or the same one, if it drives both) asserts `Analyzer.BddNodeCount` returns `null` for the same or an equivalently-shaped tree.
- [ ] Each new test is named `{Member}_{Scenario}_{Expectation}_Test`, covers one behavior, and carries an XML `<summary>`.
- [ ] The full validation list in `CLAUDE.md` passes.

**Out of scope:**
- Changing the node budget's default value or making it configurable per call.
- Any other analysis entry point's node-budget handling (rule equivalence, implication, overlap, set analysis, diff) — already covered.
