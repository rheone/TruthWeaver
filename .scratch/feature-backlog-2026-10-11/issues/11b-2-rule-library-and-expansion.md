**Parent:** [11b](11b-rule-library.md)

**What to build:** An immutable `RuleLibrary` in the `TruthWeaver` core: named rules, each with its content hash. ## Agent Brief

**Category:** enhancement
**Summary:** Add an immutable `RuleLibrary` to the core and let rule text reference a library rule with `rule("x")` or `rule("x", hash: "...")`, expanded inline at compile time.

**Current behavior:** Rule text reuses a sub-rule only through `let` definitions inside one rule. There is no way to name a compiled rule once and reference it from other rules. ADR-0019 records the design; read it and the decisions table in the parent ticket (`11b-rule-library.md`) first.

**Desired behavior:**
- `RuleLibrary` is an immutable collection of named rules. Each entry exposes the content hash the rule store already computes. The `RuleCompiler` accepts a library.
- `rule("x")` expands to the library rule's tree at compile time, using the same expansion machinery as `let` definitions. The result equals the library rule's tree and evaluates the same.
- `rule("x", hash: "<hash>")` expands only when the hash matches the library rule's current hash.
- A library rule has no parameters, no registry and no data sources of its own. Its predicates and data-source names resolve against the caller's compile.
- Diagnostics (new codes only; never reuse an existing code): a rule missing from the library, a hash that does not match (naming the rule and both hashes), a cycle across library rules (listing the path), and a library rule whose own predicates or data sources are missing in the caller (naming the library rule).

**Key interfaces:**
- `RuleLibrary` (new, public, in the `TruthWeaver` core, no new package dependency).
- The compiler options or `RuleCompiler` entry that receives a library.
- The definition-expansion machinery and the rule text parser.

**Acceptance criteria:** those in the checklist above, plus:
- [x] A library rule that references another library rule expands both levels.
- [x] Case and spelling of `rule` follow the existing keyword rules for rule text.

**Out of scope:** `call("x")` (11b-3); JSON, YAML and `RuleBuilder` references (11b-4); building the library from the rule store (11b-5); property tests (11b-6). Do not change the meaning of `let` definitions.

## Resolution (2026-11-01)

`RuleLibrary` (in the core, no new dependency), `CompilerOptions.Library`, and `rule("x")` / `rule("x", hash: "...")` in rule text, expanded inline with the definitions machinery. New diagnostics: `TRE0047` to `TRE0050` (a missing rule, a stale pin naming both hashes, a cycle with its path, and a library rule that raises an error in the caller's compile, named). Tests (red first for each slice): `RuleLibraryTests`, 16 tests. Docs: a "Library rules" section in `docs/rule-text.md`, the diagnostics table, the glossary and the doc-example checker; CHANGELOG entry under Added; the editor grammar knows `rule`.

Decisions the work took, for 11b-3 and later:
- `rule` is not a reserved word. It reads as a library reference only when a quoted string follows `rule(`, like `from(`. A predicate named `rule` behaves as before.
- The hash is SHA-256 of the UTF-8 rule text as upper-case hex, the same as `ConfigurationRuleStore.HashOf`. The core computes it itself (`LibraryRule.Hash`). A pin compares without case. 11b-5 can switch the store to the core's value.
- Every node and diagnostic from a library rule sits at the span of the reference in the caller's text.
- Follow-ups: ticket 78 (printing text that has a `rule(...)` reference throws) and ticket 79 (a library rule used inside a `FORALL` body).
